## 从一个具体的问题开始

好的技术记录，不必从宏大的结论开始。它可以来自一次接口设计的犹豫，一个需要核验的数据边界，或者一个尚未被解释清楚的失败。

这篇文章是**网站阅读样式的演示**，所有代码与表格都只是排版示例，不构成个人项目的实现说明或实验结果。你可以用它检查正文的节奏、长代码的滚动，以及手机上的阅读体验。

> 把前提说清楚，把过程留完整，再让结论站在证据上。

## 代码，也需要呼吸的空间

中英文混排时，像 `MemoryRepository` 这样的标识符应该容易辨认。代码块保留缩进，长行在容器内滚动，并提供复制按钮。

```java
// 排版示例，不代表真实项目接口。
public interface MemoryRepository {
    Optional<Memory> findById(UUID id);

    void save(Memory memory);
}
```

### 让查询表达意图

下面的 SQL 仅用于演示语法高亮与较长代码行的处理，不是性能建议，也没有对应的运行指标。

```sql
SELECT id, content, updated_at
FROM memories
WHERE project_id = :project_id AND deleted_at IS NULL
ORDER BY updated_at DESC, id DESC
LIMIT :page_size;
```

## 表格呈现边界，而非虚构指标

技术比较需要明确每一项的含义。这个表格用状态说明演示视觉样式，不包含虚构的性能数字。

| 记录项   | 应包含的内容             | 为什么保留     |
| -------- | ------------------------ | -------------- |
| 测试前提 | 环境、数据集、版本与命令 | 方便复现       |
| 观察结果 | 原始输出与异常情况       | 区分事实与解释 |
| 结论边界 | 尚未测试与无法外推的场景 | 避免过度推断   |

2. 再给出实现、例子与可回看的来源。
3. 最后留下当前局限和下一步需要验证的假设。
